## I7 — Boundary-chart policy (codified)

**Policy:** the engine never silently picks a side on a knife-edge hour. When a chart's corrected
solar time falls within `HOUR_BOUNDARY_MARGIN_MIN` (10 minutes) of a 2-hour branch-window edge,
`compute_pillars()` (`src/saju_engine/pillars.py::_hour_boundary_info`) attaches an
`hour_boundary` dict to `solar_correction`:

```json
"hour_boundary": {
  "distance_minutes": 2,
  "primary_hour_pillar": "戊寅",
  "alternate_hour_pillar": "丁丑",
  "note": "Corrected solar time is within the boundary margin of a 2-hour branch window; ..."
}
```

This reaches every consumer for free: `chart.to_json()` / `--format json` now emit both readings
(the review's specific ask), and `premium_report.py`'s existing "⚠ Hour-boundary note" disclosure
now sources its distance/alternate-pillar text from this single field instead of recomputing it
independently (the two had started to duplicate the same 120-minute-window arithmetic).

**Deliberate exclusion:** the 子 (23:00/01:00) edge does not get an alternate pillar. Crossing that
edge doesn't just flip the hour branch — under the Korean 야자시 convention it also flips which
calendar day's stem drives the hour stem, a compound decision `_hour_boundary_info` does not
attempt to re-derive. `_hour_stem_day_stem` already has separate, tested logic for that boundary.

**Tests:** `tests/test_pillars.py` — `test_hour_boundary_flag_present_for_knife_edge_chart`,
`test_hour_boundary_flag_absent_mid_window`, `test_hour_boundary_excludes_the_zi_hour_edge`,
`test_rm_boundary_case_pinned`.

## I4 finding — city geocoding is a live network call and is not stable run-to-run

While building the RM fixture for the I7 test above, recomputing RM's chart (1994-09-12, 13:28,
Seoul, UTC+9, `--city Seoul` with no explicit `--longitude`) against current `HEAD` produced:

| | `longitude` | `correction_minutes` | `solar_time` | distance to hour boundary |
|---|---|---|---|---|
| Committed `rm-report.md` (generated in `b09fa2d`) | implies ~125.9°E | -32.1 min | 12:55 | ~5 min |
| Live recompute today (`0bd6c11` + this pass, 3 repeated calls, all identical) | 126.9783°E | -27.7 min | **13:00 exactly** | **0 min** |

`pillars.py` hasn't changed the EoT/longitude formula since `b09fa2d` (`git diff b09fa2d HEAD --
src/saju_engine/pillars.py` is empty before this pass), so the only thing that can explain the
~1°/4-minute drift is the geocoder itself: `sajupy` resolves `--city` via a live Nominatim
(OpenStreetMap) lookup (`geopy.geocoders.Nominatim`, see `sajupy/core.py`), not a static table.
Three repeated calls just now all returned the identical 126.9783°E, so it isn't flaky on a
short timescale — but it is not guaranteed stable across the weeks between when RM's report was
generated and today, and there is no caching or pinning anywhere in the intake path.

**Consequence:** RM's shipped `rm-report.md` (used as a *landing-page demo*) is stale relative to
what the engine computes today, and — worse — today's reading places his hour exactly on a branch
boundary (0-minute margin), the most severe case the I7 mechanism can flag, which the shipped
report's own "~5 minutes" disclosure does not reflect.

**This is a reader decision, not a code fix:** the ground rules in `CLAUDE.md` ("no speculation,"
"decline to invent") mean this pass does not regenerate RM's report or pick between his primary
(乙未) and alternate (甲午) hour pillar. Recommended next step for whoever owns the candidate
reports: either (a) pin an explicit `--longitude` for Seoul (verified against a static source, not
live-geocoded) before regenerating, or (b) regenerate with `--city Seoul` again, note today's
0-minute margin explicitly in the report the way `rm-report.md`'s existing disclosure pattern
already does for less severe cases, and decide which hour pillar to narrate.

**Broader I4 recommendation (unchanged from the original review, now with harder evidence):**
prefer explicit `--longitude` in all intake paths; treat `--city` geocoding as advisory only,
exactly because it is a live network call with no determinism guarantee — not just because of
known-bad results like `Pallipat` → 76.33°E (the original I4 finding). The `solar_correction`
dict already carries `longitude_source` (`geocoded` vs `fallback_*`) precisely so a report's
metadata can disclose which path was used; that field should be checked/surfaced whenever a
candidate report is regenerated from a bare city name.

## Other items fixed in this pass

- **I3** — `pillars.py::_warn_if_suspicious_longitude` now checks Korean-convention UTC+9 charts
  against 127.5°E (the meridian Korea's own Saju convention corrects against) instead of Japan's
  135°E zone meridian, so a correctly-geocoded Korean city (e.g. Seoul, 126.9783°E) no longer
  trips the "verify the city name" warning. Non-Korean-convention charts and other UTC offsets are
  unaffected — confirmed `Pallipat` (I4's original case) still warns correctly.
- **I6** — `Chart.to_json()` now rounds all floats to 2 decimal places at the serialization
  boundary (`chart.py::_round_floats`), so `element_counts`/`self_score` no longer leak values
  like `1.9000000000000001` into any JSON/report surface that reads `to_json()`. `to_dict()` keeps
  full precision for internal callers. `skeleton.py`'s internal engine-draft dump was also rounded
  for the same reason.
